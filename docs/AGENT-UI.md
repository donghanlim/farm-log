# 1. 에이전트 스펙

파이프라인 5단. 각 단은 독립 함수이고, **경계는 JSON 계약**이다.

```
음성/사진 ─▶ ① 수집 ─▶ ② 추출 ─▶ ③ 검증 ─▶ ④ 보완질의 ─▶ ⑤ 저장
              STT      LLM       규칙       LLM         결정론
```

Phase 1에서 만드는 것은 **①②④⑤**. ③(농약 검증)은 Phase 2다.

## 1.1 ② 추출 에이전트

### 컨텍스트 페이로드

추출 정확도의 대부분은 프롬프트가 아니라 **여기서 나온다.**

```json
{
  "today": "2026-09-03",
  "parcels": [
    {"id":"p1","name":"3번 하우스","aliases":["3번","셋째 하우스","3동"],"area_m2":660},
    {"id":"p2","name":"윗밭","aliases":["위밭","산밭"],"area_m2":1200}
  ],
  "crops": [
    {"parcel_id":"p1","crop":"토마토","variety":"대추방울","planted_at":"2026-08-10"}
  ],
  "recent_logs": [
    "09-01 p1 방제 코니도 2000배",
    "08-28 p2 관주"
  ],
  "common_products": ["스미치온","코니도","다이센엠45"]
}
```

- `aliases` — 농민은 등록명으로 말하지 않는다. Phase 0 콘시어지에서 실제 호칭을 수집해 채운다.
- `common_products` — 최근 90일 사용 약제. **STT 오인식 교정의 핵심.** "스미치온"이 "스미치욘"으로 들어와도 복구된다.
- `recent_logs` — 생략된 주어를 복원한다. "어제 그거 또 쳤어"가 해석된다.

### 출력 스키마 (tool / structured output)

```jsonc
{
  "name": "record_work_log",
  "input_schema": {
    "type": "object",
    "properties": {
      "worked_at":  {"type": ["string","null"]},        // YYYY-MM-DD
      "parcel_id":  {"type": ["string","null"]},        // parcels[].id 중 하나만
      "crop":       {"type": ["string","null"]},
      "work_type":  {"enum": ["파종","정식","방제","시비","관수",
                              "적심","제초","수확","출하","기타", null]},
      "inputs": [{"name":"", "amount":0, "unit":"", "dilution":""}],
      "area_m2":    {"type": ["number","null"]},
      "memo":       {"type": "string"},
      "uncertain_fields": [
        {"field":"area_m2", "reason":"not_mentioned"}   // not_mentioned | unclear_audio | ambiguous_reference
      ]
    },
    "required": ["work_type", "uncertain_fields"]
  }
}
```

### 시스템 프롬프트 규칙

1. **발화에 없는 값은 채우지 않는다.** `null` + `uncertain_fields`에 사유 기록. 추정은 금지다.
2. `parcel_id`는 반드시 `parcels[].id` 중 하나. 별칭 매칭이 안 되면 `null`.
3. 날짜 언급이 없으면 `today`. "어제"는 `today-1`. **상대 표현만 해석하고, 그 외에는 추측하지 않는다.**
4. 약제명은 `common_products`와 유사도 우선 매칭. 실패해도 **들린 대로 기록**하고 uncertain 표기.
5. 한 발화에 작업이 둘 이상이면 로그를 분리해 배열로 반환한다.

> 규칙 1이 전부다. 빈칸은 되물으면 되지만, **틀린 값이 채워지면 사용자는 앱을 신뢰하지 않는다.**

### 모델 배치

| 단계 | 모델 | 이유 |
|---|---|---|
| 추출 | `claude-sonnet-5` | 구조화 + 한국어 구어 해석 |
| 보완 질의 문장 생성 | `claude-haiku-4-5` | 짧고 정형적 |
| 작업유형 재분류(폴백) | `claude-haiku-4-5` | 단순 분류 |

컨텍스트 캐싱: `parcels`·`crops`는 농가별로 거의 고정 → 프리픽스로 캐싱한다.

## 1.2 ④ 보완 질의 에이전트

- **질문 대상은 필수 4필드뿐** — `worked_at` · `parcel_id` · `crop` · `work_type`.
  선택 필드(면적·사용량)는 묻지 않는다. 2턴 예산을 여기에 쓰면 안 된다.
- 우선순위: `work_type` → `parcel_id` → `crop` → `worked_at`
- 형태: **선택지 3개 + 직접 입력.** 최근 이력 기반으로 정렬한다.
- **최대 2턴. 그 후에도 비어 있으면 비운 채 저장한다.** 목록에서 "보완 필요" 배지로 표시.

> 완결성보다 **저장 성공률**이다. 3턴째에 사용자는 앱을 닫는다.

## 1.3 실패 모드와 폴백

| 실패 | 폴백 | 원칙 |
|---|---|---|
| STT 무응답·저신뢰 | 원문 편집 화면으로. **녹음 파일은 보존** | 사용자 발화를 잃지 않는다 |
| LLM 5초 타임아웃 | 원문을 `memo`로 저장 + "나중에 정리" 큐 | 저장은 무조건 성공 |
| 오프라인 | 로컬 저장, 추출은 온라인 복귀 후 배치 | 밭에서 실패하지 않는다 |
| 필지 매칭 실패 | 필지 선택 UI 즉시 노출 (질문 예산에 미포함) | 목록 선택은 질문보다 싸다 |
| 추출 JSON 파싱 실패 | 1회 재시도 → 실패 시 원문 저장 | 재시도는 한 번만 |

## 1.4 평가 하네스

```
eval/cases.jsonl   # Phase 0 콘시어지 라벨 100건
eval/run.ts        # npm run eval
```

- 필드별 exact / normalized match (공백·조사 제거 후 비교)
- 지표 셋:
  - **필수 4필드 정확도** — 목표 ≥ 95%
  - **전체 필드 정확도** — 목표 ≥ 90%
  - **환각률** — 발화에 없는데 채워진 필드 비율. **목표 0%.** 별도로 추적한다
- 회귀 규칙: 프롬프트를 건드리는 모든 변경에서 실행. 이전 대비 2%p 하락이면 머지하지 않는다.

# 2. 기본 UI

## 2.1 설계 원칙

사용자는 **장갑을 끼고, 직사광선 아래에서, 노안으로** 이 앱을 본다.

1. 본문 18px 이상, 터치 타깃 최소 56px
2. 홈은 **녹음 버튼 하나.** 탭 바 없음
3. 상태는 색이 아니라 **글자**로 (색각·직사광선)
4. 되돌리기는 항상 가능, 삭제는 확인
5. 오프라인 상태를 숨기지 않는다 — "저장됨 · 나중에 전송"
6. 로딩 스피너 대신 **진행 문구** ("듣는 중… → 정리하는 중…")

## 2.2 화면 목록 (Phase 1 = 6개)

| # | 화면 | 역할 |
|---|---|---|
| S1 | 홈 · 녹음 | 앱의 90%. 큰 버튼 하나 |
| S2 | 확인 카드 | 추출 결과 편집·승인 |
| S3 | 보완 질의 | 빠진 필드 1개씩 |
| S4 | 일지 목록 | 날짜순, 보완 필요 배지 |
| S5 | 일지 상세·수정 | 원문 재생 포함 |
| S6 | 필지·작물 등록 | 최초 1회 + 가끔 |

## 2.3 핵심 플로우

```
S1 홈
```

# 3. 구현 계획

## 3.1 파일 구조

```
app/
  index.tsx                 S1 홈·녹음
  confirm.tsx               S2 확인 카드
  ask.tsx                   S3 보완 질의
  logs/index.tsx            S4 목록
  logs/[id].tsx             S5 상세·수정
  parcels.tsx               S6 필지·작물
lib/
  db.ts                     expo-sqlite 스키마 + 동기화 큐
  sync.ts                   큐 → Supabase (last-write-wins)
  record.ts                 녹음·업로드
  api.ts                    Edge Function 호출
supabase/
  functions/process/        STT → 추출 → (Phase 2: 검증)
  migrations/               스키마 7테이블 + RLS
eval/
  cases.jsonl               라벨 100건
  run.ts                    npm run eval
CLAUDE.md                   도메인 용어집 + 원칙
```

**Edge Function은 하나다.** STT·추출·검증을 나누지 않는다 — 왕복이 늘면 20초 예산이 깨진다.

## 3.2 데이터 흐름

```
녹음 ─▶ SQLite에 pending 로그 생성 (즉시. 여기서 이미 "저장됨")
      ─▶ 온라인이면 Edge Function 호출
           ├ CLOVA STT
           ├ 컨텍스트 조립 (SQLite에서 필지·작물·최근이력)
           └ Claude 추출 → WorkLog JSON
      ─▶ 확인 카드 표시 → 승인 → SQLite 확정 + 동기화 큐
      ─▶ 오프라인이면 큐에 남기고 복귀 시 배치 처리
```

**핵심: 저장은 네트워크와 무관하게 즉시 성공한다.** 추출은 나중에 붙어도 된다.

## 3.3 티켓 순서

| 티켓 | 주 | 내용 |
|---|---|---|
| T1 | W1 | 마이그레이션 7테이블 + RLS |
| T2 | W1 | 카카오 로그인 |
| T3 | W1 | S6 필지·작물 등록 (별칭 입력 포함) |
| T4 | W2 | 녹음 → 업로드 → CLOVA STT → 원문 화면 |
| T5 | W3 | Edge Function: 컨텍스트 조립 + 추출 |
| T6 | W3 | eval 하네스 + 라벨 100건 투입 |
| T7 | W4 | S2 확인 카드 |
| T8 | W4 | S3 보완 질의 (2턴 제한, 건너뛰기) |
| T9 | W4 | S4 목록 · S5 상세 |
| T10 | W5 | SQLite 큐 + 동기화 |
| T11 | W5 | 사진 촬영 + EXIF 필지 매칭 |
| T12 | W6 | 계측 이벤트 + 베타 배포 |

**T5·T6이 병목이다.** T6(평가 하네스)을 T5보다 먼저 끝내면, T5를 측정하면서 만들 수 있다.
